# Развёртывание (прод, Docker Compose)

Документ описывает установку CRM на один VPS с нуля, обновление, откат, резервное копирование и мониторинг. Состав окружения и требования — `docs/api-contract-m12.md`, раздел «Развёртывание». Все прод-команды выполняются из корня репозитория на сервере.

## 1. Состав

| Сервис | Назначение |
|---|---|
| `db` | PostgreSQL 16, данные в томе `pgdata`, порт наружу не публикуется. Роли `crm_migrator` (DDL, владелец схемы) и `crm_app` (DML) создаёт `deploy/db/init-roles.sh` при первом старте |
| `migrate` | Одноразово выполняет `alembic upgrade head` от `crm_migrator`; `api` и `worker` стартуют только после его успеха |
| `api` | FastAPI (uvicorn, 2 процесса) от роли `crm_app`; `read_only`, без capabilities |
| `worker` | `python -m app.worker`: периодические задачи, исходящая очередь Telegram, heartbeat |
| `web` | Статика фронтенда (PWA) |
| `edge` | nginx: TLS, заголовки безопасности, лимиты, JSON-ошибки; порты 80/443 |
| `certbot` | Продление сертификата Let's Encrypt каждые 12 часов |
| `backup` | Ежедневный `pg_dump -Fc` в 03:00 по `APP_TIMEZONE`, том `backups` |

Telegram в режиме `webhook` работает через `edge`; в режиме `polling` опрос идёт внутри `worker`. Отдельного сервиса `bot` в проде нет.

## 2. Подготовка сервера

Требования: Linux (Ubuntu 22.04/24.04 или Debian 12), 2 vCPU, 2 ГБ ОЗУ, 20 ГБ диска плюс место под дампы.

1. Обновите систему и установите Docker Engine с плагином Compose v2 (инструкция на docs.docker.com для вашего дистрибутива). Проверка: `docker compose version`.
2. Установите `git` и `make`.
3. Брандмауэр: разрешите только 22 (SSH), 80 и 443. Порт 5432 открывать не нужно, он не публикуется.
   ```
   ufw default deny incoming && ufw allow 22/tcp && ufw allow 80/tcp && ufw allow 443/tcp && ufw enable
   ```
4. Рекомендуется: вход по SSH-ключу, запрет входа root по паролю, автоматические обновления безопасности.
5. Docker должен запускаться при загрузке: `systemctl enable docker`. Контейнеры имеют `restart: unless-stopped` и поднимутся сами после перезагрузки.

## 3. DNS

Создайте A-запись (и AAAA, если есть IPv6) для домена, например `crm.example.ru`, на IP сервера. Дождитесь распространения: `dig +short crm.example.ru` должен вернуть адрес сервера. Без этого выпуск сертификата не пройдёт.

## 4. Получение кода и настройка

```
git clone <адрес репозитория> /opt/crm && cd /opt/crm
cp .env.prod.example .env.prod
chmod 600 .env.prod
```

Заполните `.env.prod` (комментарии в файле описывают каждую переменную). Обязательные:

| Переменная | Что указать |
|---|---|
| `DOMAIN` | Домен без `https://` |
| `LETSENCRYPT_EMAIL`, `LETSENCRYPT_AGREE_TOS=yes` | Почта и согласие с условиями Let's Encrypt |
| `SECRET_KEY` | `openssl rand -hex 32` |
| `POSTGRES_PASSWORD`, `DB_MIGRATOR_PASSWORD`, `DB_APP_PASSWORD` | Три разных пароля: `openssl rand -hex 24` (только hex, пароли входят в URL подключения) |
| `SEED_DIRECTOR_PASSWORD` | Пароль руководителя, удовлетворяющий парольной политике (не короче 12 символов, разные классы символов) |
| `APP_TIMEZONE` | IANA-зона, по умолчанию `Europe/Moscow` |
| `APP_VERSION` | Необязательно: короткий хэш сборки, например `git rev-parse --short HEAD` |

Важно:
- `.env.prod` не попадает в git (`.gitignore`) и не должен копироваться в чаты и тикеты. Его утечка равна компрометации системы.
- Роли и пароли БД применяются только при первом создании тома `pgdata`. Смена `DB_*_PASSWORD` позже не меняет пароль в БД: выполните `ALTER ROLE` вручную и обновите `.env.prod`.
- Часовой пояс влияет на время бэкапа и на «сегодня» вне контекста точки. Расчёты по точке всегда идут в часовом поясе самой точки.

## 5. Первый запуск

1. Выпустите сертификат (один раз):
   ```
   make prod-cert
   ```
   Скрипт создаёт временный сертификат, запускает `edge`, получает настоящий сертификат Let's Encrypt через webroot (`/.well-known/acme-challenge/`) и перезагружает nginx. Для пробы без лимитов Let's Encrypt поставьте `LETSENCRYPT_STAGING=1`, затем уберите и повторите: переход на боевой сертификат требует повторного выпуска.
2. Запустите систему:
   ```
   make prod-up
   ```
   Команда собирает образы, поднимает сервисы, миграции применяются автоматически, затем ждёт `GET /api/v1/health/ready` до 120 секунд. Код выхода ненулевой, если система не готова (в конце будут показаны состояние и логи).
3. Создайте руководителя и первую точку:
   ```
   make prod-seed
   ```
   Команда идемпотентна. Войдите под логином руководителя и сменяйте пароль по политике. После первого входа удалите `SEED_DIRECTOR_PASSWORD` из `.env.prod`.

   Демо-данные для показа (необязательно, только на чистой системе):
   ```
   SEED_DIRECTOR_PASSWORD='<текущий пароль director>' DEMO_MANAGER_PASSWORD='…' DEMO_MECHANIC_PASSWORD='…' make prod-demo
   ```
   Скрипт `python -m app.demo_seed` работает только через API. Он создаёт вторую точку, менеджеров `manager1`, `manager2` и механиков `mechanic1`…`mechanic4`, а также посты, услуги, запчасти с приходом на склад, 15 клиентов с автомобилями, записи на ближайшие дни, заказ-наряды во всех статусах с оплатами, заявки на запчасти, рекомендации, расходы и схемы зарплаты. Пароли `DEMO_*` передаются только в окружении вызова и должны соответствовать политике паролей (от 10 символов); в `.env.prod` их не храните. `SEED_DIRECTOR_PASSWORD` из окружения вызова имеет приоритет над `.env.prod`. Если `manager1` уже существует, скрипт ничего не делает. Если прогон прервался на середине, повторный запуск не досоздаст недостающее: перед показом лучше начать с чистой БД.
4. Проверьте: `https://<домен>/` открывает экран входа; `curl -sI https://<домен>/` показывает `Strict-Transport-Security`, `Content-Security-Policy`; `curl -sI http://<домен>/` перенаправляет на HTTPS; `https://<домен>/api/docs` возвращает 404.

Сертификат продлевает контейнер `certbot` (раз в 12 часов проверяет срок; перевыпуск за 30 дней до окончания). `edge` перечитывает сертификаты каждые 6 часов. Проверка продления без выпуска:
```
sh deploy/scripts/compose.sh run --rm --no-deps --entrypoint certbot certbot renew --dry-run
```

### Без домена (http://IP:порт)

Временный режим, когда домена ещё нет или порты 80/443 заняты другими проектами на сервере.

1. В `.env.prod`: `DOMAIN=<IP сервера>`, `HTTP_PORT=8088` (любой свободный порт).
2. `make prod-up`, затем `make prod-seed`. Шаг `make prod-cert` пропускается: сертификат не нужен.

При заданном `HTTP_PORT` скрипты подключают `docker-compose.ip.yml`:
- `edge` слушает только `HTTP_PORT` с шаблоном `deploy/nginx/nginx.http.conf.template`; 80/443 не занимаются, `certbot` не запускается;
- backend получает `INSECURE_HTTP=true`: refresh-cookie без флага `Secure` (иначе браузер не сохранит её по http) и без HTTPS-заголовка HSTS.

Ограничения: трафик не шифруется, PWA не устанавливается, офлайн-кэш и service worker не работают (браузеры включают их только по HTTPS). Порты, опубликованные Docker, открыты наружу в обход ufw.

Переход на домен: направьте DNS на сервер, очистите `HTTP_PORT`, задайте `DOMAIN=<домен>` и выполните шаги 1–4 выше. Если 80/443 заняты другим прокси (Caddy, nginx), добавьте в него сайт домена с проксированием на `127.0.0.1:<HTTP_PORT>`, оставьте `HTTP_PORT` и задайте в `.env.prod` `PUBLIC_BASE_URL=https://<домен>` и `INSECURE_HTTP=false` (TLS тогда завершает внешний прокси).

## 6. Telegram

Создайте бота у BotFather, получите токен и имя. В `.env.prod`:

```
TELEGRAM_MODE=webhook
TELEGRAM_BOT_TOKEN=...
TELEGRAM_BOT_USERNAME=...
TELEGRAM_WEBHOOK_SECRET=<случайная строка 32+ символов: A-Z a-z 0-9 _ ->
```

Примените настройки и зарегистрируйте вебхук:

```
make prod-up
make prod-telegram-webhook
```

Вебхук ведёт на `https://<домен>/api/v1/telegram/webhook`; Telegram подписывает запросы секретом, лишние запросы отклоняются (тело ограничено 64 КБ). Привязку чатов и точек выполняют в интерфейсе (модуль 7). Если Telegram не нужен, оставьте `TELEGRAM_MODE=off`: очередь уведомлений не обрабатывается, воркер не считается неисправным.

## 7. Обновление

```
git pull
make prod-up
```

Образы пересобираются, перезапускаются только изменившиеся сервисы; миграции применяются сервисом `migrate` до запуска `api` и `worker`. Простой не превышает нескольких секунд (перезапуск контейнеров), данные не теряются. Перед обновлением с миграциями схемы рекомендуется свежий дамп: `make prod-backup`.

Проверка после обновления: `make prod-up` завершился кодом 0; в интерфейсе руководителя на главной блок «Система» показывает актуальную версию и свежий heartbeat воркера.

## 8. Откат

1. Если обновление не содержало миграций схемы: `git checkout <предыдущий коммит>` и `make prod-up`.
2. Если содержало, откат кода без отката схемы допустим, когда новые миграции только добавляют таблицы и столбцы (старый код их игнорирует). Иначе восстановите БД из дампа, сделанного перед обновлением (раздел 9), и только затем переключите код на предыдущий коммит.
3. Откат схемы командой `alembic downgrade` выполняется вручную и только если известно, что миграция обратима и данные не пострадают:
   ```
   sh deploy/scripts/compose.sh run --rm --no-deps migrate alembic downgrade -1
   ```
   Миграция `0012` намеренно не ослабляет права ролей при откате.

## 9. Резервные копии и восстановление

**Автоматически.** Сервис `backup` ежедневно в 03:00 по `APP_TIMEZONE` делает `pg_dump -Fc`, проверяет дамп (`pg_restore -l`), кладёт его в том `backups` как `crm-ГГГГММДД-ЧЧММСС.dump`, обновляет метку `last_success` (время показывает блок «Система») и удаляет дампы старше `BACKUP_RETENTION_DAYS` суток (30 по умолчанию).

**Немедленный дамп:** `make prod-backup`.

**Проверка восстановления** (рекомендуется после первой настройки и далее ежемесячно):

```
make prod-restore-check
```

Скрипт разворачивает последний дамп во временную БД `crm_restore_check`, проверяет, что в ней есть пользователи, а версия миграции равна `head` кода, и удаляет временную БД. Рабочая БД не затрагивается.

**Выгрузка дампов за пределы сервера.** Диск сервера не заменяет резервную копию: копируйте дампы на внешнее хранилище, например по cron:
```
docker run --rm -v crm_backups:/backup:ro -v /srv/offsite:/out alpine sh -c 'cp -u /backup/crm-*.dump /out/'
```
и далее `rclone`/`rsync` на удалённый сервер или S3-совместимое хранилище. Имя тома — `crm_backups` (проект `crm`). Дампы содержат персональные данные клиентов: храните и передавайте их только в зашифрованном виде.

**Восстановление в боевую БД** (авария). Остановите приложение, разверните дамп поверх существующей БД (объекты пересоздаются, владельцы и права берутся из дампа) и запустите заново:

```
sh deploy/scripts/compose.sh stop api worker
DUMP=$(sh deploy/scripts/compose.sh exec -T backup sh -c 'ls -1t /backup/crm-*.dump | head -n 1' | tr -d '')
sh deploy/scripts/compose.sh exec -T backup cat "$DUMP"   | sh deploy/scripts/compose.sh exec -T db pg_restore -U crm -d crm --clean --if-exists
make prod-up
```

Для другого дампа подставьте путь вида `/backup/crm-ГГГГММДД-ЧЧММСС.dump` в `DUMP`. Предупреждения вида «does not exist, skipping» при `--clean` нормальны. После восстановления проверьте вход и блок «Система». Данные, внесённые после времени дампа, потеряны: поэтому перед рискованными операциями делайте `make prod-backup`. Перенос на новый сервер: выполните разделы 2 и 4, `make prod-cert`, запустите `db` (`sh deploy/scripts/compose.sh up -d db`), восстановите дамп командой выше (имя файла передайте через `cat` с локальной машины вместо `backup`), затем `make prod-up`.

## 10. Мониторинг

| Что | Как |
|---|---|
| Готовность | `GET https://<домен>/api/v1/health/ready`: `200` и `status` `ok` или `degraded`, `503` и `status: down` при недоступности БД или несовпадении версии миграций. Без аутентификации, версий и секретов не раскрывает |
| Живость | `GET /api/v1/health` |
| Подробности | Блок «Система» на главной руководителя (`GET /api/v1/system/status`, только директор): версия, миграции, воркер, очередь Telegram, время последнего бэкапа |
| Контейнеры | `docker compose --env-file .env.prod -f docker-compose.prod.yml ps` (колонка health) |
| Логи | `make prod-logs`; ротация `json-file` 10 МБ × 5 файлов на сервис |

Внешний мониторинг (UptimeRobot, Better Stack и т.п.): проверка `https://<домен>/api/v1/health/ready` раз в минуту; алерт на код `503` и на `degraded` дольше 10 минут. Смысл статусов:

- `degraded` с `worker.ok=false`: воркер не пишет heartbeat (упал или завис). `docker compose ... restart worker`, затем логи `worker`.
- `degraded` с `outbox.ok=false`: самое старое сообщение в очереди Telegram старше `READY_OUTBOX_MAX_AGE_SECONDS` (300 с): проверьте токен бота, доступность `api.telegram.org`, логи воркера.
- `down`: недоступна БД или версия миграций не равна `head` (миграции не применены): логи `db` и `migrate`.

## 11. Безопасность эксплуатации

- Доступ к серверу только по ключам; `.env.prod` с правами `600`, владелец администратор.
- Процессы контейнеров не от root, файловые системы `api`, `worker`, `web` только для чтения, `cap_drop: [ALL]`, `no-new-privileges`. `db` и `edge` стартуют от root только на время инициализации и затем сбрасывают права.
- Приложение подключается к БД ролью `crm_app` без прав DDL; журналы (`audit_log`, `stock_movements`, `payments`, `payroll_adjustments`) неизменяемы: у роли нет `UPDATE`/`DELETE`/`TRUNCATE`.
- Клиентский IP для лимитов определяется по заголовку, который перезаписывает `edge`; API доступен только из внутренней сети compose.
- В логах нет паролей, токенов, содержимого сообщений Telegram и тел запросов.

## 12. Частые проблемы

| Симптом | Причина и решение |
|---|---|
| `make prod-up` завершился неготовностью, `migrate` с ошибкой | Логи: `sh deploy/scripts/compose.sh logs migrate`. Частая причина: неверные пароли в `.env.prod` относительно созданного тома `pgdata` |
| `edge` не стартует: нет файла сертификата | Не выполнен `make prod-cert` |
| `make prod-cert`: ошибка проверки домена | DNS не указывает на сервер, закрыт порт 80 или другой процесс слушает 80/443 |
| В интерфейсе «Сервис временно недоступен» | `api` перезапускается или остановлен: `ps`, логи `api` |
| Блок «Система»: последний бэкап не указан | Бэкап ещё не выполнялся: `make prod-backup` |
| Вход после обновления не работает, а `ready` показывает `down` | Миграции не применены: логи `migrate` |
