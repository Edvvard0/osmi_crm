## 1. Цели и рамки

**Что делаем.** PWA-платформу для управления сетью автосервисов с направлением детейлинга. Система собирает данные о работе каждой точки: записи, заказ-наряды, работа механиков, склад, касса, расходы. На их основе руководитель получает отчёты и считает зарплату.

**Ключевые требования**

| Требование | Решение |
|---|---|
| Несколько точек | Все операционные данные привязаны к `location_id`. Пользователь имеет доступ к одной или нескольким точкам, руководитель — ко всем |
| Два направления | Каждая услуга, пост и заказ-наряд помечены отделом: `service` (сервис) или `detailing` (детейлинг). Заказ может быть `mixed` |
| Роли | Механик, менеджер, руководитель (RBAC с проверкой доступа к точке) |
| Вход | Только логин и пароль. Email и почтовый сервис не используются. Учётные записи создаёт руководитель |
| Уведомления | Только Telegram-бот |
| Платформа | PWA: устанавливается на телефон и ПК, адаптивная вёрстка |
| Развёртывание | Всё в Docker: разработка, тесты и прод запускаются только в контейнерах (раздел 3.4) |
| Ошибки | Пользователь видит только понятные сообщения. Трейсбеки, SQL и внутренние детали остаются в логах сервера (раздел 4.6) |
| Файлы | Фото и загрузка файлов в системе не предусмотрены |
| Безопасность | Защита всех полей ввода от SQL-инъекций, XSS и других инъекций (раздел 4.1) |
| Качество | Каждый модуль покрыт автотестами и проверяется вручную по чек-листу |

**Что не входит в первую версию** (требует отдельного решения, см. раздел 7)
- Фискализация платежей (54-ФЗ, онлайн-касса). В CRM платежи только учитываются.
- Личный кабинет клиента и онлайн-запись с сайта.
- Интеграции с 1С и поставщиками запчастей.

## 2. Технологический стек

### Backend
| Компонент | Технология |
|---|---|
| Язык | Python 3.12 |
| Веб-фреймворк | FastAPI (полностью асинхронный код) |
| ORM | SQLAlchemy 2.0 (async, `AsyncSession`), драйвер `asyncpg` |
| Миграции | Alembic (async env) |
| Валидация | Pydantic v2, `pydantic-settings` для конфигурации |
| СУБД | PostgreSQL 16 (расширения `pg_trgm`, `btree_gist`, `citext`) |
| Rate limit | в памяти процесса + таблица `login_attempts` в PostgreSQL (без Redis) |
| Фоновые задачи | asyncio-задачи внутри приложения (outbox в PostgreSQL): отправка в Telegram, ежедневные сводки |
| Telegram | `aiogram` 3 (webhook в проде, polling локально) |
| Хеширование паролей | Argon2id (`argon2-cffi`) |
| Токены | JWT (`pyjwt`) для access и непрозрачный refresh-токен в БД |
| Санитизация текста | `nh3` (удаляет HTML из свободного текста) |
| PDF (печать заказ-наряда) | WeasyPrint + Jinja2 с `autoescape=True` |
| Логи | `structlog`, JSON-формат |

### Frontend
| Компонент | Технология |

| Графики | Recharts |

### Инфраструктура и качество
| Компонент | Технология |
|---|---|
| Контейнеры | Docker + Docker Compose: отдельные конфигурации для разработки, тестов и прода (раздел 3.4) |
| Обратный прокси | Nginx: TLS, заголовки безопасности, раздача статики |

| Безопасность | pip-audit, npm audit, semgrep, Trivy (сканирование Docker-образов), OWASP ZAP baseline (в модуле 12) |

### 3.2 Слои backend

```
router  →  service  →  repository  →  SQLAlchemy (AsyncSession)
  │           │
  │           └─ бизнес-правила, транзакции, публикация событий в outbox
  └─ Pydantic-схемы на вход и выход, зависимости: текущий пользователь, проверка роли и точки
```

- Роутеры тонкие: принимают схему, вызывают сервис, возвращают схему ответа (`response_model`). ORM-объекты наружу не отдаются.
- Права проверяются дважды: зависимость `require_role(...)` на эндпоинте и фильтр по разрешённым `location_id` в репозитории. Так закрываются и вертикальная, и горизонтальная (IDOR) эскалация.
- События (заказ создан, работа назначена и т.д.) пишутся в таблицу `notification_outbox` в той же транзакции, что и бизнес-изменение. Отдельный воркер отправляет их в Telegram. Сообщения не теряются при сбоях Telegram API.
- Денежные суммы считаются только на сервере (`Decimal`), клиент присылает количество и скидку, но не итоги.

### 3.3 Процессы в проде

Каждый процесс — отдельный Docker-контейнер.

| Процесс | Назначение |
|---|---|
| `api` | uvicorn + FastAPI, также принимает webhook Telegram |
| `worker` | фоновая задача: отправка outbox, ежедневные сводки, очистка просроченных сессий |
| `postgres` | хранилища |
| `nginx` | TLS, статика фронтенда, проксирование `/api` |

### 3.4 Docker

Разработка, тесты и прод запускаются только в контейнерах. На машине нужен Docker (на Windows — Docker Desktop). Python, Node.js и PostgreSQL локально ставить не нужно.

| Окружение | Файл | Контейнеры |
|---|---|---|
| Разработка | `docker-compose.yml` | `postgres`, `migrate` (разовый запуск `alembic upgrade head`), `api` (uvicorn с `--reload`, код подключён томом), `worker`, `bot` (Telegram в режиме polling), `frontend` (Vite dev server с hot reload), `nginx` |
| Тесты | `docker-compose.test.yml` | `postgres-test` (данные в `tmpfs`, после прогона ничего не остаётся), `backend-tests` (pytest), `frontend-tests` (Vitest), `e2e` (образ Playwright) |
| Прод | `docker-compose.prod.yml` | `postgres` (именованный том), `migrate`, `api`, `worker`, `nginx` (внутри собранный фронтенд), `certbot`, `backup` (pg_dump по расписанию) |

**Образы**
- Backend: multi-stage сборка на `python:3.12-slim`, зависимости через `uv`, в финальном образе нет компиляторов и dev-зависимостей.
- Frontend: сборка на `node:20-alpine`, результат копируется в `nginx:alpine`.
- Все контейнеры работают от непривилегированного пользователя, у каждого есть `healthcheck`, `api` стартует только после успешного `migrate`.
- Версии базовых образов зафиксированы. CI сканирует образы Trivy и не пропускает уязвимости уровня High и Critical.

**Сеть и данные**
- В проде наружу открыт только `nginx` (порты 80 и 443). PostgreSQL доступен только во внутренней сети Docker.
- Данные PostgreSQL и бэкапы лежат в именованных томах, пересборка и перезапуск контейнеров их не затрагивают.
- Секреты передаются через `.env` (в проде — Docker secrets), в образы не попадают.

**Команды** (`Makefile`; в Windows запускаются из Git Bash или WSL, рядом в README указаны эквиваленты `docker compose ...`)

| Команда | Действие |
|---|---|
| `make up` / `make down` | Поднять / остановить окружение разработки |
| `make logs` | Логи всех контейнеров |
| `make migrate` | Применить миграции |
| `make seed` | Заполнить демо-данными |
| `make test` | Все тесты в `docker-compose.test.yml` |
| `make lint` | Линтеры и проверка типов в контейнере |
| `make prod-up` | Собрать и запустить прод |

## 4. Сквозные требования (действуют для каждого модуля)

### 4.1 Безопасность

#### Аутентификация и сессии
- Пароли хешируются Argon2id. Минимум 10 символов, проверка по списку распространённых паролей. Пароль не может совпадать с логином.
- Руководитель задаёт сотруднику начальный пароль. Сотрудник может сменить его сам в разделе «Настройки»; принудительной смены после входа нет.
- Защита от перебора: не больше 10 попыток входа в минуту с одного IP (в памяти / таблица `login_attempts`), блокировка учётной записи на 15 минут после 5 неудачных попыток подряд, уведомление руководителю в Telegram. Ответ на ошибку входа одинаковый для неверного логина и неверного пароля.
- Access-токен JWT живёт 15 минут и хранится только в памяти приложения, не в `localStorage`.
- Refresh-токен живёт 14 дней. Хранится в cookie `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth`. В БД лежит только его SHA-256 хеш. При каждом обновлении токен ротируется. Повторное использование старого токена отзывает всю цепочку сессий (reuse detection).
- При смене пароля, блокировке или смене роли все сессии пользователя отзываются.

#### Авторизация
- RBAC по ролям `mechanic`, `manager`, `director` (матрица в разделе 4.5).
- Каждый запрос к данным точки фильтруется по списку точек пользователя. Объект чужой точки возвращает 404, а не 403, чтобы не раскрывать его существование.
- Идентификаторы — UUID, перебор по порядку невозможен.

#### Защита от инъекций (все поля ввода)
| Угроза | Мера |
|---|---|
| SQL-инъекции | Только SQLAlchemy Core/ORM с параметрами. Конкатенация SQL и f-строки в `text()` запрещены (ruff `S608`, semgrep-правило в CI). Поля сортировки и фильтров принимаются только из белого списка (`Literal[...]`). В поиске `LIKE` спецсимволы `%` и `_` экранируются |
| XSS (хранимый и отражённый) | Свободный текст очищается от HTML через `nh3` перед сохранением. React экранирует вывод, `dangerouslySetInnerHTML` запрещён правилом ESLint. Строгий CSP без `unsafe-inline` для скриптов |
| Mass assignment | Отдельные Pydantic-схемы `Create`, `Update`, `Read`, у всех `extra="forbid"`. Поля `role`, `location_id`, `status`, суммы клиент изменить напрямую не может |
| Невалидные данные | Pydantic: `str_strip_whitespace`, ограничения длины на каждой строке, регулярные выражения для телефона (E.164), госномера, VIN, логина. Числа с границами (`ge`, `le`). Удаление управляющих символов из строк. Лимит размера тела запроса |
| Вредоносные файлы | Загрузка файлов не предусмотрена: эндпоинтов приёма файлов нет, запросы `multipart/form-data` отклоняются |
| CSV/формульные инъекции в экспорте | Значения, начинающиеся с `= + - @ \t \r`, экранируются префиксом `'` |
| HTML-инъекции в Telegram | Все пользовательские данные в сообщениях проходят `html.escape` (режим `parse_mode=HTML`) |
| Template injection (PDF) | Jinja2 с `autoescape=True`, пользовательские данные передаются только как переменные |
| Header / log injection | Переводы строк удаляются из значений в заголовках и логах. Логи структурированные (JSON) |
| ReDoS | Длина строки проверяется до регулярного выражения, регулярки без вложенных квантификаторов |
| CSRF | Access-токен передаётся в заголовке `Authorization`. Refresh-cookie `SameSite=Strict`, эндпоинт обновления дополнительно требует заголовок `X-Requested-With` |

#### Транспорт и заголовки (Nginx)
- Только HTTPS, HSTS.
- `Content-Security-Policy: default-src 'self'; script-src 'self'; img-src 'self' blob: data:; connect-src 'self'; object-src 'none'; frame-ancestors 'none'; base-uri 'self'`.
- `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`, `Permissions-Policy` (камера, микрофон и геолокация запрещены), `server_tokens off`.
- CORS разрешён только для домена фронтенда.

#### Данные и инфраструктура
- Приложение подключается к БД ролью без прав суперпользователя. Миграции выполняет отдельная роль. Для таблицы `audit_log` у роли приложения нет прав `UPDATE` и `DELETE`.
- Секреты только в переменных окружения, `.env` в `.gitignore`, в репозитории лежит `.env.example`.
- Контейнеры запускаются от непривилегированного пользователя, PostgreSQL не доступен снаружи Docker-сети.
- Ежедневный `pg_dump` с хранением 30 дней. Восстановление из бэкапа проверяется в модуле 12.
- Персональные данные клиентов (телефоны, ФИО) не пишутся в логи.
- Telegram webhook проверяет заголовок `X-Telegram-Bot-Api-Secret-Token`.

### 4.2 Тестирование

Каждый модуль сдаётся с тремя уровнями тестов и ручным чек-листом.

| Уровень | Инструменты | Что покрывает |
|---|---|---|
| Unit | pytest | Бизнес-правила сервисов: переходы статусов, расчёт сумм, остатки, зарплата |
| Integration (API) | pytest + httpx + реальный PostgreSQL в тестовом контейнере | Каждый эндпоинт: успех, ошибки валидации, коды ответов |
| Права доступа | параметризованные pytest-тесты | Каждый эндпоинт × каждая роль × своя/чужая точка |
| Безопасность | общий набор payload-ов из `tests/security/payloads.py` | Каждое текстовое поле модуля получает SQLi, XSS, null-byte, юникод-трюки, сверхдлинные строки. Ожидается: 422 или безопасное сохранение без исполнения |
| Frontend | Vitest + RTL + MSW | Формы (валидация), ключевые компоненты, отображение по ролям |
| E2E | Playwright (desktop 1440px и mobile 390px) | Основной сценарий модуля целиком через UI |

**Пороги покрытия (CI блокирует merge при падении ниже):**
- backend — не менее 85% строк, для модулей auth, cash, warehouse, payroll — не менее 95%;
- frontend — не менее 70%.

**Изоляция тестов:** каждый тест выполняется в транзакции с откатом. Тестовые данные создаются фабриками.

### 4.3 Качество кода и процесс
- pre-commit: ruff (lint + format), mypy, ESLint, Prettier.
- Ветка на модуль → Pull Request → CI зелёный → merge → тег `module-N` → обновление демо-стенда.
- Все команды разработки и тестов выполняются внутри контейнеров (раздел 3.4). CI использует тот же `docker-compose.test.yml`, что и разработчик.
- Команда `make seed` создаёт демо-данные: 2 точки, по пользователю каждой роли, клиентов, авто, каталог услуг. Пароли демо-пользователей задаются переменной `SEED_PASSWORD` в `.env`.
- Документация API генерируется автоматически (`/api/docs`, доступна только в dev).

### 4.4 Адаптивность и PWA
- Mobile-first вёрстка. Контрольные ширины: 360, 390, 768, 1024, 1440 px.
- Таблицы на мобильных превращаются в карточки. Формы занимают весь экран (bottom sheet).
- Экраны механика проектируются в первую очередь для телефона: крупные кнопки (от 56 px), минимум ввода с клавиатуры.
- PWA: manifest, иконки, установка на домашний экран, service worker кэширует оболочку приложения. В офлайне показываются последние загруженные данные и баннер «Нет соединения». Действия, меняющие данные, в офлайне блокируются с понятным сообщением.

### 4.5 Матрица прав

| Действие | Механик | Менеджер | Руководитель |
|---|---|---|---|
| Видеть точки | свои | свои | все |
| Клиенты и авто | только в своих работах (ФИО, авто) | просмотр и редактирование в своих точках | всё |
| Записи (календарь) | просмотр своих | создание и изменение | всё |
| Создать заказ-наряд | — | ✓ | ✓ |
| Назначить механика | — | ✓ | ✓ |
| Изменить статус работы | только свои работы | ✓ | ✓ |
| Видеть цены и суммы заказа | — | ✓ | ✓ |
| Комментарии к заказу | ✓ (свои заказы) | ✓ | ✓ |
| Заявка на запчасть | создать | одобрить / отклонить | ✓ |
| Склад: приход, списание | — | своя точка | все точки + перемещения |
| Принять оплату | — | ✓ | ✓ |
| Возврат, отмена оплаты | — | — | ✓ |
| Расходы точки | — | создать | всё |
| Отчёты | свой заработок | операционный отчёт своей точки | все отчёты, финансы |
| Зарплата | свой заработок | — | расчёт, корректировки |
| Тепловая карта активности | своя | механики своих точек | все сотрудники |
| Пользователи, точки, каталог и цены | — | просмотр каталога | ✓ |
| Журнал действий | — | — | ✓ |

### 4.6 Обработка ошибок: никаких внутренних деталей на клиенте

Пользователь никогда не видит трейсбеков, текста SQL, имён таблиц и ограничений, путей к файлам, версий библиотек и технических сообщений браузера. Подробности ошибки пишутся только в лог сервера.

#### Backend
- В проде `debug=False`. `/api/docs`, `/api/redoc` и `/openapi.json` отключены.
- Глобальный обработчик: любое необработанное исключение превращается в ответ 500 `{"error": {"code": "internal_error", "message": "Внутренняя ошибка", "request_id": "7f3a9c..."}}`. Трейсбек пишется в лог вместе с `request_id`.
- Ошибки БД (`IntegrityError`, нарушение exclusion-ограничения и т.п.) переводятся в доменные коды: `duplicate_phone`, `post_busy`, `insufficient_stock`. Имена ограничений и текст SQL наружу не уходят.
- Ошибки валидации (422) отдаются в своём формате: поле, код, сообщение по-русски. Служебные поля Pydantic (`input`, `ctx`, `url`) вырезаются, введённое значение не возвращается.
- Nginx и uvicorn не отдают заголовки `Server` и `X-Powered-By`. Для 502, 503 и 504 у Nginx свои страницы и JSON-ответ без технических подробностей.

#### Frontend
- **Единый API-слой.** Любая ошибка запроса превращается в объект `AppError { kind, code, fields?, requestId? }`. Компоненты не выводят `error.message` от сервера или браузера: текст берётся из словаря сообщений по коду, для неизвестного кода — общее сообщение.

| Ситуация | Поведение интерфейса |
|---|---|
| Нет сети, таймаут | Баннер «Нет соединения с сервером» и кнопка «Повторить» |
| 400 / 422 | Ошибки под соответствующими полями формы |
| 401 | Тихое обновление токена; при неудаче — экран входа с сообщением «Сессия истекла» |
| 403 | «Недостаточно прав для этого действия» |
| 404 | Экран «Не найдено» |
| 409 | Диалог «Данные изменил другой сотрудник» с кнопкой «Обновить» |
| 429 | «Слишком много попыток, повторите через N секунд» |
| 5xx и неизвестные | «Что-то пошло не так. Попробуйте ещё раз» и короткий код (`request_id`) для поддержки |

- **Error Boundary** — глобальный и на каждом маршруте. Если один экран упал, вместо него показывается «Не удалось отобразить страницу» с кнопками «Обновить» и «На главную», меню продолжает работать. Ошибка загрузки чанка после обновления версии вызывает однократную автоматическую перезагрузку.
- **Глобальные перехватчики** `window.onerror` и `unhandledrejection`: пользователю — общий toast, технические детали — в `POST /api/v1/client-errors` (без персональных данных, с лимитом частоты). Ошибки видит разработчик в логах, а не пользователь.
- **TanStack Query:** глобальный `onError`. Повтор только для GET при сетевых ошибках и 5xx (не больше 2 раз). Изменяющие запросы автоматически не повторяются.
- **Prod-сборка:** source maps не публикуются, `console.*` удаляются, в бандл попадают только публичные переменные `VITE_*`.

### Модуль 1. Аутентификация, пользователи, точки · M

**Цель:** вход по логину и паролю, роли, управление сотрудниками и точками.

**Backend**
- `POST /auth/login`, `POST /auth/refresh`, `POST /auth/logout`, `POST /auth/change-password`, `GET /auth/me`.
- Rate limit, блокировка после неудачных попыток, ротация refresh-токенов, reuse detection.
- Зависимости `get_current_user`, `require_role`, `get_allowed_location_ids`.
- CRUD точек (только руководитель).
- CRUD пользователей (руководитель): создание с начальным паролем, роль, привязка к точкам, блокировка, установка нового пароля, отзыв сессий.
- `POST /auth/change-password` требует текущий пароль; после смены отзываются все остальные сессии пользователя.
- Механизм журнала действий (`audit_log`): запись входов, неудачных попыток, изменений пользователей и точек. Просмотр — в модуле 11.

**Frontend**
- Экран входа, выход. После входа сразу открывается рабочий стол роли, промежуточных шагов нет.
- Layout и навигация по роли, переключатель точки в шапке.
- «Настройки» (профиль): смена пароля — текущий пароль, новый, повтор.
- Руководитель: список сотрудников, карточка, создание и редактирование. Список точек, карточка точки.
- Защищённые маршруты: недоступный экран → страница «Нет доступа».

**Тесты**
- Вход: успех, неверный пароль, несуществующий логин (одинаковый ответ), заблокированный пользователь, неактивный пользователь.
- Блокировка после 5 попыток, rate limit по IP.
- Refresh: ротация, повторное использование старого токена отзывает сессии, истёкший токен.
- Матрица прав на все эндпоинты пользователей и точек.
- Смена пароля: неверный текущий пароль, слабый новый пароль, после смены старый пароль не работает, другие сессии отозваны.
- Инъекции в логин, ФИО, адрес и название точки.
- E2E: руководитель создаёт менеджера → менеджер входит и сразу видит рабочий стол своей точки → меняет пароль в «Настройках» → входит с новым паролем.

**Ручная проверка**
- [ ] Войти как руководитель (демо-пользователь из seed).
- [ ] Создать точку, создать менеджера и механика с привязкой к точке.
- [ ] Войти как менеджер: сразу открывается рабочий стол менеджера.
- [ ] В «Настройках» сменить пароль: выйти и войти с новым паролем, старый не подходит.
- [ ] Ввести неверный пароль 5 раз: учётная запись блокируется, сообщение понятное.
- [ ] Менеджер не видит раздел «Сотрудники» и не открывает его по прямому URL.
- [ ] Ввести `<script>alert(1)</script>` в ФИО: alert не срабатывает, текст сохраняется без тегов.
- [ ] Выход завершает сессию; кнопка «Назад» в браузере не возвращает в систему.

- Таймер работы: старт, пауза, продолжение, завершение. У механика может быть только одна активная работа (уникальный частичный индекс).
- Фактическое время по журналу работ.
- Когда все работы заказа завершены, заказ автоматически переходит в `quality_check`.
- Рекомендации по авто (что заменить в следующий визит).
- Заявки на запчасти: создание механиком, одобрение или отклонение менеджером.
- Срезанное представление заказа для механика: без цен, сумм и контактов клиента.

**Frontend**
- «Мои задачи»: активная работа с таймером сверху, ниже список.
- Карточка работы: авто, жалоба, крупные кнопки «Начать / Пауза / Завершить», комментарий, рекомендация, заявка на запчасть.
- Менеджер: очередь заявок на запчасти.

**Тесты:** нельзя запустить две работы одновременно, нельзя управлять чужой работой, автопереход заказа, подсчёт времени с паузами, отсутствие цен в ответах API для механика (проверка схемы ответа), E2E на мобильном viewport.

**Ручная проверка**
- [ ] Войти механиком с телефона, увидеть назначенные работы.
- [ ] Запустить работу, поставить на паузу, продолжить, завершить: время посчитано без паузы.
- [ ] Попытаться запустить вторую работу при активной: система предлагает поставить первую на паузу.
- [ ] Оставить комментарий к работе: менеджер видит его в карточке заказа.
- [ ] Создать заявку на запчасть, войти менеджером и одобрить её.
- [ ] Убедиться, что механик нигде не видит цены.

### Модуль 7. Telegram-уведомления · M

**Цель:** сотрудники получают важные события в Telegram.

**Backend**
- Telegram-бот на aiogram. Привязка: пользователь в «Настройках» получает одноразовый код (живёт 10 минут) и ссылку `t.me/<bot>?start=<code>`, бот связывает `chat_id` с пользователем. Отвязка в «Настройках» или командой `/stop`.
- Outbox-воркер: отправка, повтор с экспоненциальной задержкой (до 5 попыток), учёт лимитов Telegram (30 сообщений в секунду), пометка ошибок. Если пользователь заблокировал бота, привязка снимается.
- Настройки: пользователь включает и выключает типы событий.
- Опционально: групповой чат точки (`locations.telegram_chat_id`) для общих событий.
- События этого этапа:

| Событие | Кому |
|---|---|
| Вам назначена работа | механику |
| Изменён срок или комментарий к вашей работе | механику |
| Заявка на запчасть одобрена или отклонена | механику |
| Новая запись создана другим сотрудником | менеджерам точки |
| Механик завершил работу / заказ готов к проверке | менеджеру заказа |
| Новая заявка на запчасть | менеджерам точки |
| Заказ просрочен по планируемому сроку | менеджеру заказа |
| Клиент не приехал на запись | менеджерам точки |
| Учётная запись заблокирована после неудачных входов | руководителю |

- Модули 8–10 добавляют свои события в тот же механизм.

**Frontend**
- «Настройки» (C-02): «Подключить Telegram» (код, ссылка, QR-код), статус подключения, переключатели событий.

**Тесты:** привязка (истёкший код, повторное использование кода), экранирование HTML в сообщениях, повторы при ошибке API (мок Telegram), снятие привязки при `403 Forbidden`, проверка секрета webhook, сообщения только тем, у кого событие включено.

**Ручная проверка**
- [ ] Подключить Telegram механика и менеджера через «Настройки».
- [ ] Назначить механику работу: ему пришло сообщение с номером заказа и авто.
- [ ] Механик завершает работу: менеджеру пришло сообщение.
- [ ] Отключить тип события в «Настройках»: сообщения перестают приходить.
- [ ] Создать клиента с ФИО `<b>Тест</b>`: в Telegram текст выводится как есть, без жирного.

### Модуль 10. Отчёты, аналитика, зарплата · L

**Цель:** руководитель видит работу всех точек и считает зарплату.

**Backend**
- Дашборд: выручка, количество заказов, средний чек, загрузка постов, доля детейлинга, конверсия «запись → визит», новые и повторные клиенты. Фильтр по точке и периоду, сравнение с прошлым периодом.
- Отчёты: выручка по точкам и отделам, по услугам, по механикам (нормочасы план и факт, выработка), склад (оборот, маржа на запчастях), расходы и прибыль (упрощённый P&L), клиенты.
- Зарплата: схемы оплаты (процент от работ, ставка за нормочас, оклад + процент), корректировки (премии, штрафы), расчёт за период, детализация по заказам.
- Тепловая карта активности сотрудника: `GET /api/v1/users/{id}/activity-heatmap?from=&to=` (период до 366 дней). Ответ — массив по дням: дата, отработанные часы, число работ, номера заказов (для подсказки).
  - Механик: часы из `work_logs` (сумма интервалов, пауза не учитывается). Интервал, проходящий через полночь, делится между двумя днями. Дни считаются в часовом поясе точки.
  - Менеджер и руководитель: число действий за день из `audit_log` (созданные и изменённые заказы, записи, оплаты), часы не считаются.
  - Уровень цвета: 0 — нет активности, далее 4 уровня по порогам (для механика: до 2 ч, 2–5 ч, 5–8 ч, более 8 ч). Пороги задаются в системных настройках.
  - Итоги за период: рабочих дней, всего часов, среднее в рабочий день, самая длинная серия рабочих дней.
  - Права: механик — только своя карта, менеджер — механики своих точек, руководитель — все. Чужой сотрудник → 404.
- Экспорт в XLSX и CSV (с защитой от формульных инъекций).
- Тяжёлые агрегаты — через материализованные представления с ночным обновлением либо индексированные запросы (решение по замерам).
- Ежедневная сводка руководителю в Telegram в настраиваемое время.

**Frontend**
- Дашборд руководителя с KPI-плитками и графиками.
- Конструктор отчётов: выбор отчёта, период, точка, отдел.
- Зарплата: таблица сотрудников, детализация, корректировки.
- Тепловая карта в карточке сотрудника (D-05), в карточке механика для менеджера (MG-17) и в «Моём заработке» механика (M-07); оформление — раздел 2.9 документа экранов: сетка «недели × дни недели» за 12 месяцев в стиле календаря GitHub, подписи месяцев, легенда «меньше → больше», подсказка по наведению или касанию («Вт, 14 октября · 7 ч 20 мин · 3 работы»), клик по дню открывает список работ за день. На телефоне — по умолчанию последние 3 месяца с горизонтальной прокруткой. Цвета — оттенки accent, работают в светлой и тёмной теме, у каждой ячейки есть `aria-label`.
- Механик: «Мой заработок» за период.
- Менеджер: операционный отчёт точки.

**Тесты**
- Корректность каждого агрегата на контрольном наборе данных (эталонные суммы), граничные даты и часовые пояса, все схемы зарплаты, экспорт со строками `=CMD()`, права (менеджер не видит финансы других точек), производительность (отчёт за год по 100 тыс. заказов быстрее 2 секунд).
- Тепловая карта: сумма часов по дням с паузами, интервал через полночь, часовой пояс точки (работа в 23:30 по Владивостоку попадает в правильный день), незавершённая работа считается до текущего момента, пустые дни возвращаются с нулём, период больше 366 дней отклоняется, права (механик не видит чужую карту, менеджер — сотрудников чужой точки), производительность (год по одному сотруднику быстрее 200 мс).
- Frontend: уровни цвета по порогам, подсказка, отображение на мобильном viewport.

**Ручная проверка**
- [ ] Сверить выручку дашборда за день с кассовым отчётом.
- [ ] Открыть отчёт по механикам: нормочасы совпадают с выполненными работами.
- [ ] Назначить механику 40% от работ, рассчитать зарплату за месяц.
- [ ] Открыть карточку механика: на тепловой карте отмечены дни, когда он работал; подсказка показывает часы и число работ; клик по дню открывает его работы.
- [ ] Войти механиком: в «Моём заработке» видна своя тепловая карта, чужую по прямому URL открыть нельзя.
- [ ] Выгрузить отчёт в Excel, открыть его.
- [ ] Получить ежедневную сводку в Telegram.

## 7. Открытые вопросы

Ответы влияют на детали модулей. До ответа приняты решения по умолчанию (указаны курсивом).

1. **Фискализация.** Нужна ли интеграция с онлайн-кассой (АТОЛ, Эвотор и т.п.)? *По умолчанию — нет, только учёт платежей.*
2. **Видит ли механик цены?** *По умолчанию — нет, только свой заработок.*
3. **Схема зарплаты механиков.** Процент от работ, нормочас, оклад? Отличается ли у детейлеров? *По умолчанию поддерживаются все три схемы.*
4. **Уведомления клиентам** («Ваш автомобиль готов») через того же Telegram-бота? *По умолчанию — нет, в таблице клиентов зарезервировано поле `telegram_chat_id`.*
5. **Переход между точками.** Может ли механик работать в нескольких точках? *По умолчанию — да, через привязку к нескольким точкам.*
6. **Импорт данных** из текущей системы (Excel, YCLIENTS, 1С)? *По умолчанию — нет.*
7. **Хостинг.** VPS в РФ (152-ФЗ о персональных данных)? *По умолчанию — VPS в РФ.*
8. **Количество точек и пользователей** на старте и через год — для расчёта нагрузки. *По умолчанию — до 10 точек и 150 пользователей.*
